## 阻断问题

### [P1] B09 专用工作台未拒绝宿主 URL session 与服务端身份不一致

`plugins/paint/web/src/PaintWorkbench.tsx:20-23` 初始化时直接接受 `/context` 返回的身份并加载其 binding，没有像原共享工作台 `packages/workbench-common/src/Workbench.tsx:34` 那样比较 `new URLSearchParams(location.search).get('session')` 与 `id.session_id`。因此 iframe 或直接页面仍带旧聊天 session 时，不会 fail-closed，而会静默打开当前 cookie 对应的另一个 session 工程。

独立 Playwright 反例先证明 Three.js 画布不是 API 假选面：清空下拉值后直接点击真实 canvas，得到 `selected_index="2"`、`已选 1 个面`。随后在同一受控隔离宿主中访问 `.../satellite-paint/?session=stale-session`，页面无任何 alert，`viewer_count=1`、`data-ready=true`，并显示 `alice / a-session`。反例进程 exit 1；原始脚本与结果见 `docs/evidence/B09/review/ui-counterexample.mjs`、`ui-counterexamples.json`。

影响：宿主选择的聊天/session 与实际写入工程可能错配。后端仍按当前凭据授权，因而这不是跨 owner 读取，但它破坏 B09 明确要求的跨会话上下文一致性和旧 iframe fail-closed 语义；编辑、保存、恢复或导出可能落到用户当前 cookie 的错误聊天工程。该问题属于允许延期的正式 DSH 外部缺口之外的隔离开发范围，不能用 B07 blocked 豁免。

现有 `tests/e2e/paint-workflow.spec.ts` 只在正常 session 中完成流程，并在流程结束后更换 cookie 验证已加载页面被清空；它没有覆盖“页面首次加载时 URL session 已与服务端身份不一致”。因此 3/3 browser 通过未发现本回归。
